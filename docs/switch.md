# Nintendo Switch target

The user's Switch runs Atmosphère (custom firmware). Target: homebrew NRO (devkitPro/libnx); an NSP would need the
user's own `prod.keys` (Lockpick_RCM) and is not planned until the game runs well.

Status (2026-10-16, test port, branch `agent/switch` of the runtime, worktree `ext/PS2Recomp-kl-switch`): the
whole port (6.4k recompiled functions, native VU1 and IOP code, native GS renderer, libmpeg2) builds as one NRO and
runs in the Citron emulator without stalls or crashes (EE, VU1, GS renderer and sound all working, ~11 guest frames/s),
but the picture cannot be checked there: Citron cannot run Mesa nouveau's shaders, so every GS render target stays
black. Next step: the user's real Switch; see "Test in Citron".

## Toolchain (in WSL Ubuntu, as root)
- devkitPro's installer/apt host is blocked for scripted downloads (Cloudflare), so Ubuntu's
  `pacman-package-manager` is configured for devkitPro repos: `/opt/devkitpro/pacman.conf`, wrapper
  `/usr/local/bin/dkp-pacman`, mirror pkg.devkitpro.org over HTTPS.
- **Security caveat:** `SigLevel = Never` (keyring host also blocked) → packages are not signature-verified.
  Restore signature checking when the keyring can be fetched.
- Installed: switch-dev (devkitA64 GCC 16.1.0, libnx 4.12.0), switch-sdl2 2.28.5, switch-glfw 3.3.4,
  switch-mesa 20.1.0 (EGL + glapi + nouveau: desktop OpenGL 4.3 core, GLSL 4.30), switch-glad, switch-ffmpeg 7.1,
  switch-zlib. raylib 5.5 is fetched by CMake and built with PLATFORM=SDL. CMake 4.2, Ninja.
- Root git: `safe.directory '*'` (repo lives on /mnt/c).

## Build
    MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -u root -- bash -c 'cd "/mnt/c/Users/lovas/Claude/God Of War/ext/PS2Recomp-kl-switch" && ./switch/build.sh'
- `switch/build.sh` configures with devkitPro's `Switch.cmake` into `~/gow-switch-build` (the WSL file system: much
  faster than /mnt/c) and builds `ps2xRuntime/ps2EntryRunner.nro` (~70 MB). Full build ~40 min on the dev PC (one
  unity batch of generated code takes ~20 min by itself); incremental runtime changes a few minutes.
- Inputs are the same as the PC build: the generated runner code in `ps2xRuntime/src/runner/` (git-ignored), the
  native IOP code `ps2xIOP/src/native/iopn_*.cpp` (git-ignored), and the VU1 C++ generated by a PC build:
  `PS2X_VU1_PREGENERATED_DIR` (default `../PS2Recomp-kl/out/build-kl/ps2xRuntime`, its `vu1_generado/` and
  `vu1n_generado/`); a cross build cannot run the generator it would compile for the target.
- Switch-only build settings: runtime-only build, raylib SDL platform without raudio, no LTO (GCC LTO over the
  generated code takes hours), `-fsigned-char` (x86 behaviour of plain `char`), sse2neon's precise min/max (NaN bit
  patterns used as large values), division, square root and dot products, logs off, FFmpeg off (libmpeg2).

## Controls (ps2_pad.cpp, libnx HID; user decision 2026-10-25)
- Default, Nintendo style: **A = Cross, B = Circle, X = Square, Y = Triangle**, + = Start, - = Select, L/R = L1/R1,
  ZL/ZR = L2/R2, stick clicks = L3/R3, D-pad = D-pad. `GOW_PAD_POSITIONAL=1` in env.txt: by position instead
  (B = Cross, A = Circle, Y = Square, X = Triangle; the layout before update_swfix3).
- On-screen button icons: still the PS2 symbols on the console; the Switch letters exist as `_nx` language overlays
  (tools/gow_pad_icons.py, docs/settings.md "Button icons"), checked on the PC only (2026-10-26).
- Sticks: HID stick positions (+-32767) -> DualShock analog bytes (0x80 centre, y inverted), the pad reports analog
  mode (0x73). Left stick = movement, right stick = evade roll (God of War's camera is fixed: no camera stick).
  Until update_swfix3 the sticks did nothing on the console: gow_overrides.cpp `gowPad2ReadState` replaced them
  with keyboard sticks whenever raylib saw no gamepad, and the deko3d build has no raylib window, so raylib never
  sees one (centre every frame). The keyboard fallback is now not built for `PS2X_DK`.

## What the Switch build does differently (all behind `__SWITCH__` / `PLATFORM_SWITCH` / `PS2X_IS_SWITCH`)
- **GS renderer context** (gs_gl.cpp): its own EGL OpenGL core context (4.6 → 4.5 → 4.3, surfaceless), the same GL
  entry-point list as Windows (`loadApi`), `glTextureBarrierNV` when `glTextureBarrier` (4.5) is missing. Frames are
  presented through the RAM path (readback + raylib texture upload); the Windows zero-copy shared texture is WGL-only.
- **Sound**: raylib's audio module does not exist on Switch; the sound engine's callback (s16 stereo 48 kHz) is
  played through SDL2 audio (ps2_runtime.cpp). The Windows device selection (ps2_audio_device.cpp) and the
  XInput/HID rumble are not built; rumble goes through raylib's `SetGamepadVibration` (SDL).
- **Window**: 1280x720 (`InitWindow`), paths with `sdmc:` kept as they are.
- **Start-up** (ps2_switch_runtime.cpp, libnx `userAppInit`):
  - logs to `nxlink -s` when a PC listens, else to `sdmc:/switch/gow/log.txt`;
  - `sdmc:/switch/gow/env.txt`: `KEY=VALUE` lines, the Switch counterpart of play.cmd's `set` lines (e.g.
    `GOW_SCALER=bilinear`, `GOW_PERF_DIAG=1`);
  - defaults `PS2X_GS_WORKER=1`, `GOW_GS_FINISH_ASINCRONO=1`, `GOW_MC0=sdmc:/switch/gow/play.mcd`;
  - a libnx exception handler logs crashes (`[switch] EXCEPTION pc=... (elf+offset)`, registers) for
    `addr2line -e ps2EntryRunner.elf <offset>`.
- **Threads**: libnx starts every thread on the default core and Horizon does not time-slice threads of one
  priority, so `ThreadNaming::SetCurrentThreadName` pins them: GameThread (EE + IOP) core 1, GSWorker (VIF1/VU1)
  core 2, presentation / GS frontend / GL backend core 0. Every pthread (std::thread too) gets priority 0x3B, below
  the main thread's 0x2C, so a busy main thread starves the other core-0 threads.
  - **Stacks**: libnx gives a pthread 128 KiB unless a size is set; the runtime's threads were sized by Windows'
    1 MiB default and the VIF1/VU1 worker overflowed on its first VU1 job (it jumped to 0 and Citron silently
    suspended it; the EE then waited forever for the GS FINISH interrupt in vid::WaitForDMAComplete 0x17A2A0). The
    NRO links with `--wrap=pthread_create` (ps2_switch_runtime.cpp): threads without an explicit size get 1 MiB.
  - `std::thread::detach()` throws on libnx (no pthread_detach): keep thread objects alive instead.
- **Frame pacing**: raylib's `WaitTime` has no sleep call on Horizon, so `SetTargetFPS` would busy-wait the whole frame
  on the main thread. The window uses `FLAG_VSYNC_HINT` instead (the swap blocks at the display's 60 Hz).
- **GL driver lock** (`GSSharedPresent::DriverMutex`, gs_shared_present.h): Mesa nouveau is not thread-safe across
  contexts (buffer objects and command buffers are shared without locking); with the host window's context on the
  main thread and the GS renderer's context on the GS thread, concurrent use freed buffer objects twice and corrupted
  the heap (~15 s in, when real rendering and the RAM-frame readback start). The GS thread holds the lock while it
  executes a command chunk; the main thread from after the frame latch to the end of `EndDrawing`.
- Boot ELF default `sdmc:/switch/gow/disc-usa/SCUS_973.99`; the extracted disc folder next to it (docs/disc.md).

## SD card layout
    sdmc:/switch/gow/gow.nro              the NRO (any name)
    sdmc:/switch/gow/disc-usa/            the extracted disc (SCUS_973.99, IRX, GODOFWAR.TOC, PART1/2.PAK, .disc_layout, .disc_meta)
    sdmc:/switch/gow/play.mcd             memory card (copy of disc-usa/play.mcd)
    sdmc:/switch/gow/env.txt              optional settings
    sdmc:/switch/gow/log.txt              written by the NRO
The PAKs are 4 GB each: the SD card must be exFAT (FAT32 has a 4 GB file limit).

## Installable NSP (user 2026-10-16: install with DBI from the PC, game data inside the NSP)
- Title ID 0100D0D0600A0000, name "God of War", publisher Waffle565. The RomFS holds `disc-usa/` (the extracted
  disc without memory-card files, ~8.2 GB); `main.cpp` boots `romfs:/disc-usa/SCUS_973.99` when it exists, otherwise
  the SD path (NRO). The SD folder `sdmc:/switch/gow/` (created at start) keeps log, memory card and env.txt. As an
  installed application the game gets full application memory (no "hold R over a game").
- Needs the user's own `prod.keys` (Lockpick_RCM on the console); never commit or share them. Installing a
  self-built NSP needs Atmosphère's signature patches (as for any homebrew NSP).
- Packer: hacBrewPack v3.05 built from source in WSL (`/root/nsp-tools/hacBrewPack`; the original The-4n repo is
  deleted, mirror github.com/rlaphoenix/hacBrewPack; `apt install build-essential` first), with `port/switch/nsp/hacbrewpack_version.patch` applied (`git apply` in
  `/root/nsp-tools/hacBrewPack`, then `make`; adds the version, see below). hactool (SciresM, built in
  `/root/nsp-tools/hactool`) reads a built NSP back (`-t pfs0`, then `--romfsdir` on the control NCA; give it the same
  filtered key file as build_nsp.sh).
- Steps: `port/switch/nsp/make_romfs_links.sh` (Git Bash: RomFS tree of NTFS hard links, no 8 GB copy), then in WSL
  `port/switch/nsp/build_nsp.sh <prod.keys>` (elf2nso → exefs/main, npdmtool gow.json → main.npdm, nacptool +
  default icon → control, hacbrewpack --nologo) → `port/switch/nsp/out/*.nsp`. The NSP contains the game data: only
  for the user's own console.
- `gow.json` (NPDM) is nx-hbloader's `hbl.json` (`hbl.json.ref`) with: program_id fields (newer npdmtool), 39-bit
  address space (type 3), application_type 1, no map_region and no debug_flags (Citron rejects the load with
  error 32 otherwise), hbloader's filesystem_access.
- Home-menu name and icon: `nacptool` writes the name for 12 of the 16 NACP languages, `build_nsp.sh` copies
  entry 0 into all 16; the icon is `port/switch/nsp/icon.jpg` (256x256 baseline JPEG, 4:2:0, no EXIF; source image
  `icon_src.png`), copied as `icon_<Language>.dat` for every language.
- **Why the home menu showed "?" (2026-10-25, screenshots `port/switch/shots/icon/`)**: two things.
  (1) The icon of the first NSP (10-16) was libnx's `default_icon.jpg`, a JPEG with **4:4:4** chroma and optimized
  Huffman tables: the console does not show it (home menu and sphaira draw "?"; test title with that icon, 2026-10-25,
  name read fine). A 4:2:0 baseline JPEG (what PIL writes with `subsampling=2`, port/switch/nsp/icon.jpg) shows.
  (2) Later NSPs had a good icon (sphaira's Games list showed it from the installed control data) but the home menu
  kept "?": every NSP was v0, and the home menu shows the new icon once the content meta version goes up (test title:
  v0 -> v65536 install refreshed it; a same-version reinstall through sphaira is skipped by its "skip if already
  installed", so that case was not measured directly). Fix: hacBrewPack patched
  (`port/switch/nsp/hacbrewpack_version.patch`, env `HBP_TITLE_VERSION` -> content meta version) and `build_nsp.sh`
  takes `VERSION=<n>`: a package with a new icon or name must use a version above the installed one (65536, 131072,
  ...). Installed 2026-10-25: GoW v65536 with the user's icon (`icon_src_2048.jpg` -> icon.jpg, 256x256 Lanczos,
  baseline 4:2:0), control-only package (below): the home menu shows it.
- `build_nsp.sh` also takes `TITLE`, `APP_NAME` (not `NAME`: WSL sets that to the host name), `ICON`, `ROMFS` and
  `OUT` for small test packages.
- **Control-only package** (new icon or name, ~0.5 MB instead of 8.5 GB): `REUSE_NSP=<the installed NSP>
  VERSION=<above the installed one> build_nsp.sh <keys>`. The content meta lists the installed NSP's program NCA (record
  read from its cnmt with hactool, `HBP_REUSE_PROGRAM` in the patched hacBrewPack) plus the new control NCA; the package
  carries a 0-byte placeholder under the program's name, so it needs sphaira with "skip if already installed" on
  (sphaira's installer checks `ncmContentStorageHas` and skips that NCA; with the option off it would install the empty
  file). `port/switch/nsp/pfs0.py` lists / extracts an NSP's small entries. The 10-18 NSP (program
  f9795578e30c19d3f6422d18e299026b, 8.57 GB) is kept as `out/base_20261018_v0.nsp` for this.
  Proven 2026-10-25: test title (icon shows, the reused program starts) and God of War (installed v65536 = that program
  + the new control). **The installed GoW is now v65536**: the next icon/name change needs `VERSION=131072`, any full NSP
  at least that too (a lower version is refused without sphaira's "allow downgrade").
- Installing an NSP without USB: copy it to `sdmc:/nsp/` over FTP (`tools/switch_ftp.py put <nsp> nsp`), then in
  sphaira (the hbmenu tile) L = file browser -> `nsp` -> the file -> "Install Selected files?" Sì (installs to the SD
  card, ~14 MB/s). DBI started from sphaira crashes ("Il software è stato chiuso a causa di un errore"). sphaira's

- Output name: `out/God of War.nsp` (user 2026-10-18); older builds are named by title id.
- Code-only update without reinstalling (`port/switch/nsp/make_update.sh`, WSL, after switch/build.sh): Atmosphère's
  loader takes a title's ExeFS from `sdmc:/atmosphere/contents/0100D0D0600A0000/exefs/` (`main` + `main.npdm`)
  when that folder exists, so a new build is ~35 MB instead of the 8.5 GB NSP; the game data stays in the
  installed NSP's RomFS. Output `out/update/atmosphere/...` (`DEST=<dir>` also copies it there); the user copies
  the `atmosphere` folder to the SD root. A full NSP is only needed when the RomFS, the title metadata or the icon
  changes; after installing a newer full NSP, delete that exefs folder or the older program keeps overriding it.
- Getting the log off the console: DBI → "Run MTP responder", USB cable, then
  `powershell -ExecutionPolicy Bypass -File tools\switch_pull_log.ps1` copies `sdmc:/switch/gow/{log,log_prev,env}.txt`
  into `port/switch/logs/<date>/` (MTP has no drive letter: the script walks the Windows shell namespace). Each
  launch rotates `log.txt` to `log_prev.txt`.
- v14 on the console (2026-10-18, first remote run): the purple screen is gone, the title menu shows (probe FAILED as
  in Citron, then RAM frames). Menu: guest ~17 fps, window 21-26 Hz; GPU present 4.2 ms/span (was 17 in v13's
  bisect estimate); GPU busy only ~31 % (bisect `gpu` ~310 ms/s) while the GS GL thread is busy ~77 % of the time
  (`call` 43 s + `vrun` 38 s of 96 s busy in 125 s): the menu is now bound by that thread's CPU work, not by the GPU.
- v15 (ext agent/switch 4137512, ccb8845, bbf2b4b; measured on the console through the remote loop, logs
  `port/switch/logs/20261018_v15*`): title menu guest **17 -> 25-26 fps**, GS GL thread busy 4.3 -> 2.0 s per 5 s;
  gameplay (ship, fighting) 9-12 fps. What each step found and changed, in order:
  - `call` was the RAM-frame present: per vsync latch the frontend ran Flush + Sync + Present as blocking round trips
    and the HW backend read the frame with a synchronous glReadPixels, so the guest waited for the GL queue and the
    GPU, and CPU submission and GPU work never overlapped. Now the threaded backend queues the present and returns
    the newest finished frame (`QueuesPresentation`, `GOW_GS_ASYNC_READBACK=0` restores the old path); the frame is
    packed into a client-storage buffer behind a fence and collected by a later present.
  - glReadPixels into a pixel pack buffer is still CPU work on switch-mesa: ~16 ms per 640x448 frame
    (`[gs-hw-present] readpixels_ms`). A compute shader (`packProgram`, same bytes and row order) does the copy on
    the GPU: 1.2 s -> 4 ms per 5 s. Map + copy of a finished buffer: ~1.7 ms per frame.
  - A present whose display registers and displayed targets' `RenderTarget::version` (draws, shuffles, clears) did
    not change only collects: the host latches at every vsync, the menu flips every 2-3.
  - Texture decodes: the game uploads its textures into GS memory again every frame, each upload invalidated the
    decoded textures there, and every decode (CPU deswizzle + glTexImage2D) cost ~3.5 ms (~100 per second in the
    menu, `[gs-hw-cpu] tex_ms` 2.3 s per 5 s). An invalidated texture whose memory still hashes to what it was
    decoded from (or to one of its three earlier contents, kept as GL textures: animated textures alternate) is valid
    again: 0 decodes in the menu, 21 -> 25 fps.
  - Host (Switch, RAM frames): the GL driver lock is only taken for GL work; a latched frame equal to the one shown,
    or a pass without a new vsync, is neither uploaded nor redrawn. Redrawing held the lock ~7 ms per pass ~45 times
    a second; in gameplay the GL thread waited 1.8 s of 5 s for it, now ~0.6 s.
  - GPU diagnostics (`GOW_GS_HW_STATS`, `GOW_GS_GPU_TIME`, `GOW_GPU_BISECT`) are opt-in again (env.txt `=1`): the
    bisect phases draw wrong pictures on purpose. `GOW_GS_HW_STATS=0` now really turns the stats off.
  - Diagnostic lines (GOW_PERF_DIAG, on by default on the Switch): `[gs-hw-cpu]` (draw() parts: pre/state/tex/post,
    vertex upload, decodes and re-validations), `[gs-hw-present]` (full vs collect-only presents, pending draws
    flushed, pack time), `[gs-host]` (host passes, unchanged frames, latch/copy/lock-wait/upload/draw+swap time).
  - Left: in the menu the GL thread is no longer the limit (VU1 `vu_ms` ~4.0 s and EE ~2.0 s per 5 s are). In
    gameplay nearly every present is a full one (~50 per second for ~10 guest frames): the game changes DISPFB1
    every field between frame buffers 0x68 and 0xd0 (with a line offset) and blends read circuits 1 and 2 at 50 %
    (PMODE 0x8026; `GOW_GS_HW_DISPLOG=1`, `port/switch/logs/20261018_v15disp`), so each vsync composes a different
    picture; and the GL thread is busy ~3.4 s per 5 s (present ~1.1 s, clut ~0.8 s, vrun ~0.9 s, texflush
    ~0.45 s). Sharing the GS texture with the host (probe FAILED on switch-mesa) would remove the per-field
    readback, the copies and the host upload altogether; short of that, the CLUT loads (~150 us each) and the
    present composition are the GL thread's next costs.
  - Remote loop notes: pad mapping see "Controls" (since update_swfix3 A = Cross, so New Game is A, A); botbase
    clicks of 50 ms can be missed at 25 fps, `cmd configure buttonClickSleepTime 120` makes them reliable; botbase
    `cmd setStick LEFT|RIGHT <x> <y>` (hex, -0x8000..0x7FFF) drives the sticks.
- v16 window presentation (ext agent/sw-present; logs `port/switch/logs/20261018_swp1*`, 2026-10-19): the GS
  renderer's own context draws and swaps the window, so a frame never leaves the GPU and the host thread does no GL.
  - Why not shared textures: switch-mesa's shared EGL contexts do not see each other's textures (the shared probe
    reads back wrong on the console and in Citron). Instead `GSSharedPresent::CaptureHostContext` takes SDL's window
    surface and its EGL config id, releases the host context (`eglMakeCurrent(NONE)`), and `GSGL::Context::Create`
    makes the GS context current on that surface (same config; `eglSwapInterval` 0). `GSSharedPresent::WindowPresent()`
    then holds; env.txt `PS2X_GS_WINDOW_PRESENT=0` restores the old shared-texture / RAM-frame paths.
  - `GSHwBackend::Present` composes the read circuits into `presentTex` as before and `presentToWindow` blits it
    into the window at 16:9 (linear, flipped to the window's bottom-up rows) and swaps; an unchanged present (same
    display registers and target versions) skips the composition and the swap. Black when PMODE shows nothing.
  - `GSHostPresentation::renderFrame` in this mode only latches one Present per vsync, polls input and sleeps 2 ms:
    no upload, draw, swap or GL driver lock on the host (the GL thread's lock wait went from 0.5-0.8 s to <1 ms per
    5 s). switch-mesa answers 0x0 to `eglQuerySurface(EGL_WIDTH)`; `GSGL::WindowSize` falls back to 1280x720.
  - Console: title menu 25-26 -> **26-27 fps** (picture correct at 1280x720); gameplay (ship, fighting) **9-13 fps,
    unchanged**. `[gs-hw-window]` (GOW_PERF_DIAG): blit ~12 ms but **eglSwapBuffers ~1.7 s per 5 s, ~28 ms per full
    present**: the swap waits for the GPU to finish the frame's work (the old RAM path hid that wait behind its
    fence). The GL thread is busy ~3.9 s of 5 s in gameplay: swap ~1.7 s, draws ~1.4 s (`[gs-hw-cpu]` post_ms ~1.0 s
    for ~7700 draw calls: ~130 us of Mesa/nouveau CPU per draw call), clut ~0.9 s (mostly pending draws it flushes),
    texflush ~0.5 s. VU1 ~2.6 s and EE ~2.3 s per 5 s.
  - Conclusion: on Mesa nouveau both the per-draw CPU cost and the GPU time per frame are far from 60 fps; the
    renderer has to move to deko3d (devkitPro's low-level NVN-style API for the Tegra X1: `deko3d` 0.5.0 and the
    `uam` shader compiler are installed in the toolchain; Nintendo's own NVN is an NDA SDK and cannot be used in
    homebrew). That is a port of `gs_hw_backend.cpp`'s GL calls (render targets, textures, samplers, the draw,
    present, CLUT, shuffle and pack shaders through uam, texture barriers, dual-source blend, compute) to deko3d
    command buffers, with CPU-visible memory replacing the readbacks.
  - Tools: `port/switch/nsp/make_update_to.sh <elf> <out dir>` packages any build's ExeFS without touching
    `out/update` (v15's package is kept in `out/update_v15`).

## Switch-speed test on PC (tools/switch_throttle)
Citron has no CPU-speed limit (its JIT runs at host speed), so neither it nor the PC build shows how slow the
console is. `tools/switch_throttle/switch_throttle.exe` runs a program at roughly the CPU power a Switch game gets:
- 3 cores (affinity to logical CPUs 0, 2, 4: one per physical core, the SMT siblings stay free); a game gets 3 of
  the 4 Cortex-A57 cores.
- every thread suspended and resumed in a 4 ms period, running `--ratio` of it (default 0.15 = 600 us of 4000),
  so all threads slow down by the same factor. 0.15 = Cortex-A57 at 1785 MHz vs one Ryzen 9 5900X core, from
  public single-core benchmarks (Tegra X1 ~250 vs 5900X ~1650 in Geekbench 5): an estimate, not a measurement.
- the GPU is not limited (the Switch's Maxwell GPU is far weaker than the PC's), and the PC build runs x86 SSE
  code where the Switch runs sse2neon, so the console can only be slower still.
Use: `bash tools/switch_throttle/build.sh` once, then `SWITCH_THROTTLE=1 tools/perf_run.sh <name> <s>`
(`SWITCH_THROTTLE_ARGS="--ratio 0.2 --cores 3"` to change it), or `switch_throttle.exe [options] -- <command>` /
`--pid N` for any process (Citron too, though its JIT adds its own cost on top).
First result (2026-10-16, PC main runner, user's save, menu → load): 43-45 guest fps unthrottled, **16.5-17 throttled**,
the same as Citron (16.5) and the user's "unplayable" on the console; the load did not reach gameplay in 240 s.

### Per-thread budget (how to read a PC run for the Switch)
The four busy threads (EE `GameThread`, VIF1/VU1 `GSWorker`, GS frontend `GSStage`, GL backend `GSThread`) form a
pipeline and get one Switch core each at ~0.15 of a PC core, so the slowest one sets the frame rate:
**Switch fps ~ PC fps x 0.15 / (busiest thread's share of one PC core)**. 60 fps on the Switch needs every thread
below ~15 % of a PC core at 60 fps on PC.
- Measure: a PC build of the Switch branch (`ext/PS2Recomp-kl-switch/out/build-pc`, Release + `/MAP`), run with the
  Switch defaults `PS2X_GS_WORKER=1 GOW_GS_FINISH_ASINCRONO=1` (`EXE_DIR=... tools/perf_run.sh`), then
  `python -I tools/thread_cpu.py <pid> 10` in gameplay (per-thread % of one core, by thread name) and
  `tools/sample_prof.py --exe <exe> --dll-exports` for the hot functions per thread.
- 2026-10-17, user's save, gameplay start (heavy) / walking: GameThread 66 / 56 %, GSWorker 60 / 36 %, GSStage
  56 / 31 %, GSThread 54 / 31 % -> estimate 14-16 fps, matching Citron. The game draws ~20k triangles per frame
  (almost all strips), each built and queued on its own; no synchronous GS round-trips in gameplay
  (`GOW_GS_INVENTORY`: cpuRead, clears, snapshots 0).

### Changes from it
- EE checkpoint fast path (ext agent/switch cba2dfc): `EeScheduler::checkpointDueFast` handles the generated code's
  checkpoints (tens of millions per second) with a few adds while no EE timer step, IOP batch, scheduled event or
  slice end is due; the full checkpoint runs at exactly the same calls as before (timer/IOP cycles are handed over
  there or at any EE timer register access). The per-checkpoint bookkeeping was ~28 % of the EE thread.
  GameThread 66 -> 39 % / 56 -> 30 %. Gate port/swfast/gate/20261017_011443 zones 0-4 60 fps speed 1.00, savetest ok.
- GS draw-state serial: `GS::m_stateSerial` is bumped by every GS register write except vertex data (RGBAQ, ST, UV,
  FOG, XYZ*), which is where all draw state comes from; `buildDrawBatch` rebuilds the ~200-byte `GSDrawState` only
  when it changed, and `GSPrimitiveBatch::stateSerial` lets the GL-thread queue (`GSThreadedBackend::Enqueue`) and
  `GSHwBackend::submit` skip their whole-state `memcmp` for every triangle of a strip (equal serial = equal state;
  serial 0 = compare as before). The shuffle path's per-8x8-block `unordered_map` lookup is a 64-entry array.
  GSStage 54 -> 49 %, GSThread 61 -> 46 % (heavy window; runs vary by a few points). Replay captures made before
  this change no longer load (the header's batch size differs).
- Triangle runs: `GS::vertexKick` collects the primitives drawn with one state (`GSPrimitiveVerts`: vertices + serial;
  `GSPrimitiveBatch` = that + `GSDrawState`) and hands them over in one `GSRasterBackend::SubmitRun` (default: one
  `Submit` each). The run is flushed before every register write that can change state (which also precedes
  LoadClut, BeginTransfer, TEXFLUSH and FINISH), before image data, and when each locked entry point returns
  (`FlushRunAtExit` in processGIFPacket, processNativePackedGIFPacket, writeRegister), so it is empty whenever
  m_stateMutex is free and the backend sees the same calls in the same order. The GL-thread queue carries a run as
  one `VerticesRun` op; `GSHwBackend::submitRun` sends the first primitive through `submit` (all state decisions)
  and, for triangles, only adds the vertices of the rest. GSStage 49 -> 45 %, GSThread 46 -> 44 % (small: what
  is left in GSStage is the per-vertex GIF register decoding).

- Bug found: GCC's default `-ffp-contract=fast` fused multiply + add into FMLA (one rounding): 220 of 1832 recorded
  gameplay runs differed from the PC build (1-ulp values, larger through P/Q). The Switch build now passes
  `-ffp-contract=off` (ps2xRuntime/CMakeLists.txt); all 1832 then match. It cost no speed (fusion was rare).
- Changes, all bit-exact (1832 records, 0 differences on x86 and ARM):
  - `vu1n_gen.py --locals` (passed by the branch's CMake): each block keeps the VU registers it uses in C++ locals,
    loaded at entry, stored back at every exit (the data-memory stores through `n.data` may alias the VU1State, so the
    compiler could not keep them in registers before).
  - Self-loops: a block that branches back to its own start repeats inside its function with the registers still in
    locals; `VU1NativeAccess::chainTo` does what runNative does between two blocks (timing/history entry, FDIV
    retire, stop/budget check, next start cycle and tail record); runNative finishes the block the function returns
    from (`ctx.slot`, `kVu1nFinished`).
  - Flag rings with 8 slots: a push no longer copies the evicted writer (it stays at slot next-5).
  - ARM: `madd`'s overflow test is one UMAX + one compare, and its wide fallback runs inline in double NEON lanes (no
    call, so no vector register spills); `nrm` is BIC + UMIN + BSL (3 ops instead of 4, same bits); runNative counts
    pairs only with GOW_VU1N_DIAG.
- Result (A57 cost per warm replay pass of 100 gameplay runs, the replay's own hashing excluded): 12.3 M -> 9.1 M
  (-26 %); generated blocks 8.5 M -> 6.3 M, dispatch 2.8 M -> 2.3 M. Expected on the console: vu_ms about a quarter lower.
- Tried and dropped (no gain on the A57): going straight on to other successor blocks, as one function per group of
  blocks with gotos (GCC spilled the vector registers across the large functions) or by guaranteed tail calls
  (`chainTo` costs about what runNative's dispatch does). Left: runNative's ~100 instructions per block, the flag-ring
  pushes and tail stores at block exits.

- EE generated code (ext agent/sw-ee3 d352c1c, 2026-10-19; regenerate all runner files with
  `ps2_recomp port/usa/recomp-clock.toml`, then a full build): two recompiler changes that make every guest
  instruction cheaper, most of all on AArch64 (docs/runtime-changes.md has the details):
  - JALR callers are no longer "fully resumable". An unresolved JR/JALR gave every instruction of the function a
    label and an entry case; for a call that is never needed. 1079 functions (109k instructions) had only JALRs,
    among them the hottest EE function 0x162F18 (~12 % of the EE thread); the labels kept the C++ compiler from
    carrying anything across instructions and reset the recompiler's constant tracking at each one.
  - `ctx->pc` is stored only where the runtime can read it: no store for pure arithmetic; a load/store publishes its
    PC only on the macros' special-address path (`ps2_gen_pc`); main RAM is one compare. On AArch64 every guest
    access used to carry a mov/movk/str for the PC (and kept the previous instruction's store alive).
  - Measured: PC build, Switch layout, gameplay: EE thread busy 31.2 -> 26.6 % of samples (0x162F18 4.6 -> 2.9 %);
    x86 stores a constant PC in one instruction, so ARM gains more: devkitA64 -O2 output of 0x162F18 68.3k -> 50.1k
    instructions, no PC store left between guest memory accesses. Gate zones 0-4 60 fps speed 1.00 (slot 0 capture
    5 differs, a combat scene, as in the v13/v15 gates), savetest ok.
  - Looked at and left: the EE copies every VIF1 DMA chain into a buffer for the GS worker, ~105 MB/s in gameplay
    (2 chains of ~900 KB per frame; on PC ~12 % of the EE thread's samples land in vcruntime's copy routines).
    Handing the worker guest RAM instead would need the game never to rewrite data still queued (skinned vertex
    buffers are rebuilt every frame), so it stays. Guest thread switches leave generated code by a C++ throw
    (`EeDispatcherTransfer`): ~100 per second in gameplay (interrupt handlers), ~4 ms per second on PC: not a cost.

  (gsq_wait ~10.9 s = two threads idle), ~13.9k draws in 68 batches per frame. The user saw only one core busy:
  the spinning EE. A pipeline that idle while the EE spins points at a wait/wake problem on Horizon, not raw CPU
  speed; the v6 log decides whether it is still there.
- NSP v8 (same file, 2026-10-17 evening): still ~1 frame per 6 s (user: "10 frames per minute"), but the EE no
  longer spins: ee_ms ~300-480 and guest_wait_ms ~5000-6700 per 5.7-7.6 s window (asleep), VIF1/VU1 ~30-60 ms, GS
  frontend ~5 ms, gsq_wait ~11-15 s (both GS producers blocked on the GL thread). Per frame the GL thread had only
  ~120-300 GL draws, 44-89 barriers, ~5 MB uploads. So the whole pipeline waits on the GL thread (core 0), whose
  time no counter covered; the v2 spin was a symptom. Citron's numbers say nothing here: its shader recompiler
  rejects nouveau's shaders, so it never really renders. NSP v9 adds the `[gs-gl]` line (below) and renders at 1x.
- `[gs-gl]` (GOW_PERF_DIAG=1, every 5 s, gs_threaded_backend.cpp): GL-thread busy time, time waiting for the
  Switch driver lock, and time/count per queued op kind (`vrun` = triangle runs, `clut` = CLUT loads, which can read
  back from a render target, `present` = composing the display and its RAM readback, `upload`, `texflush`, ...).
  On PC (5 s at 60 fps): busy 1.49 s, vrun 1.12 s, clut 0.23 s/18000, present 0.04 s/300, lock wait 0.3 ms.
- NSP v9 (`log switch/log (2).txt`, 2026-10-17 night): scale 1.00, a little faster (guest_flip 0.7-0.8 Hz, was
  0.15) but still unplayable. `[gs-gl]`: the GL thread is busy ~5.9 s of every 6 s window, lock wait ~10 ms, CLUT
  loads ~20 ms; the time sits in `vrun` (draws) and `call` (present/latch) in turns, i.e. whichever GL call
  waits for the GPU. The user saw GPU 100 %, CPU 1-2 %: the console is GPU-bound on ~100 draws per frame at
  640x448, so some shader path is far too expensive on the Tegra. NSP v10 adds `[gs-gpu]` (below).
- `[gs-gpu]` (GOW_GS_GPU_TIME=1, on by default on the Switch; gs_hw_backend.cpp): GL_TIME_ELAPSED queries around
  each draw batch, shuffle flush, CLUT readback, clear and present, read back without waiting, summed per kind
  every 5 s: `kind=ms/count/Kpx` (Kpx = host pixels of the batches' bounding boxes, an upper bound). Draw kinds
  carry their shader path: T textured, I indexed (palette lookup in the shader), R render target as texture,
  X reinterpreted fetch, Z depth source, D destination alpha test, B shader blend (reads the target), A Z in
  colour memory, V barrier runs (shadow volumes), F extra fail pass, L linear filter. A span includes GPU idle
  time inside it, so on a CPU-bound PC the sum is close to the window; on the GPU-bound console it is real GPU
  time. PC at 1x (5 s, 60 fps): draw:TIFL 1.95 s, present 0.99 s, shuffle 0.85 s, draw:TBV 0.54 s.
- `[gpu-bisect]` (GOW_GPU_BISECT=1, on by default on the Switch while the GPU limit is hunted; env.txt
  `GOW_GPU_BISECT=0` turns it off; gs_hw_backend.cpp `updateBisect`): from 20 s after start the renderer runs 8 s
  phases, the baseline and one GPU feature off in turns: no-fail-pass, no-shader-blend, no-texture, point-filter,
  no-shuffle, no-draw (only clears and present), no-readback (the RAM-frame present skips its glReadPixels). The
  picture is wrong in the "off" phases. Each phase end prints mode, presents per second and GPU ms per second;
  compare an "off" phase with the baseline phases around it. A full cycle is 112 s (play ~2.5 min; with 12 s
  phases from 30 s the v12 run ended before point-filter).
- Shared-texture presentation on the Switch (agent/sw-share, merged 66651cb): the GS renderer's EGL context shares
  objects with raylib/SDL's context (captured on the main thread by `GSSharedPresent::CaptureHostContext`), so
  Present copies the composed frame into a shared, fenced texture slot (the same slot/fence/Acquire code as WGL on
  Windows) instead of glReadPixels + UpdateTexture; log lines "shared with the host window" / "host mode: shared
  texture". RAM frames stay the fallback (sharing failed, or env.txt `PS2X_GS_DIRECT_PRESENT=0`). The host thread
  then never waits for the GS thread, and Horizon does not time-slice threads of one priority on core 0, so the
  window has no vsync swap interval (the vsync wait happened inside the first GL call, under the GL driver lock):
  `renderFrame` paces at 60 Hz with a sleep after the lock is released, and a pass with no newer published frame
  only polls input and sleeps 2 ms (an unfinished frame is retried every 8 ms). Citron: 36 game fps, GL-thread lock
  wait 0.5 s per 5 s (RAM frames: 34 fps, 0.96 s). On the console (v12) the window showed only the magenta
  placeholder for the whole run: the host never got a frame it could show, though EGL sharing was created. So the
  sharing now checks itself (gs_gl.cpp `createProbe` / `checkProbe`): the GS context makes a 1x1 texture by the same
  GPU copy the frames use, the host context reads it back once before trusting any slot ("[gs-present] shared probe
  ok / FAILED"); a wrong value, or no slot completing for the host within 3 s of the first publish, prints
  "shared textures do not work here" and both sides go back to RAM frames (`GSThreadedBackend::UsesSharedPresentation`
  follows `GSSharedPresent::Active()` live). Citron with NSP v13 reproduces it: "shared probe FAILED (read
  ff0000ff)", then RAM frames; so on switch-mesa the shared context does not see the GS context's textures (a
  texture name of the other namespace, e.g. raylib's own, gets drawn: hence the magenta). The Switch therefore
  presents through RAM frames until that is solved; PC: "shared probe ok".
- NSP v12 (`log switch/log (3).txt`, 2026-10-18): magenta screen (above), ~2.6 presents/s, GPU-bound as before.
  `[gpu-bisect]`: no-fail-pass x1.48, no-shader-blend x1.08, **no-texture x18** (46.9 presents/s). `[gs-gpu]`:
  draw:TIFL (indexed, linear, fail pass) 62 % of the GPU time, ~20 ms per batch in the baseline phases and ~0.5 ms
  with texturing off. That path read each of the 4 bilinear texels with signed integer modulo for the wrap and a
  dependent index -> palette fetch chain (8 fetches); it now fetches the 2x2 indices with one `textureGather` (the
  sampler wraps: REPEAT / CLAMP_TO_EDGE from CLAMP, set per draw already) and looks up 4 palette entries; the point
  path is one nearest `texture()` + one palette fetch. Plain T/TBV spans (~12 ms with tiny areas) and present
  (~6.5 ms) look like spans that contain a flush and the GPU idle until the next submission, not real cost.
- NSP v13 (`log switch/log (4).txt`, 2026-10-18): the game runs at ~19 guest fps (v12: 0.7); draw:TIFL 0.27 ms per
  batch (was ~20). Still magenta: the probe failed (as in Citron), but `renderFrame`'s shared early return kept
  waiting for a shared frame because none had been published yet (host_hz 0); fixed (ext, update v14), Citron
